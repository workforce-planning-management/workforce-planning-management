# 独立したセキュリティテスト

**視点:** このソフトウェアを書いていない人に攻撃してもらうにはどうすればよいか、何を対象として示すべきか、見つかったことをどう扱うか。

独立したテストは行われていません。[脅威モデル](../../../../spec/governance/threat-model.md)は、ソフトウェアを書いたのと同じアシスタントが書き、ほかの誰にもレビューされておらず、そこに挙げたすべての統制は、その作成者が動作を確かめたものです。[準備状況の評価](../../../../spec/readiness-assessment.md)は、独立したペネトレーションテストを、人にしか閉じられない関門として挙げています(WPM-T201、**未実施**)。このページは、テストを依頼する人のためのブリーフです。テスターが作成したテスト計画ではなく、それに代わるものでもありません。

## 開始前に決めておくルール

自社のセキュリティ部門や法務部門と埋めてください。ここでは何も決めていません。

- **権限:** テストが承認されたものであることを誰が署名するか。対象のシステムとアドレス。
- **期間:** 日付と時間帯(暦日で数える)と、中止するときの連絡先。
- **範囲:** 対象に含めるもの(API、インターフェース、サインインのフロー、バックアップのスクリプト)と、含めないもの(ID プロバイダー自体のサービス、自社のネットワーク、他のシステムと共有するもの)。
- **データ:** 合成データのみ。テスターが実在の個人データを見つけた場合に、誰に知らせ、どう扱うか。
- **破壊的なテスト:** サービス拒否、大量の書き込み、消去を許可するか、許可するならどこでか。
- **報告:** 形式、深刻度の尺度、受け取る人、保管できる期間、見つけたシークレットの扱い。
- **再テスト:** 契約に修正の確認が含まれていること。

## 所見をどうするか

1. それぞれを、テスターの参照番号、証拠、付けられた深刻度とともに、[tasks.md](../../../../spec/tasks.md) のタスクとして記録します。異論のある所見は、理由とともに異論ありとして記録したままにします。
2. 最初に失敗するテストを書いて修正します。修正がルールであれば脅威モデルのギャップ欄に加え、再テストに合格したときにだけそこで閉じます。
3. 報告書が手元にあり、すべての所見に担当者がいて、再テストが完了するまで、WPM-T201 を完了にしないでください。同じ変更で[準備状況の評価](../../../../spec/readiness-assessment.md)と関門の一覧(WPM-T203)を更新します。
4. 悪用可能な内容が含まれる場合は、報告書をリポジトリの外に置き、保管場所へリンクします。

## 問題のない報告書の意味と、意味しないこと

所見のないテストが示すのは、このテスターたちが、この期間に、この範囲とこれらの ID で、何も見つけなかったということです。欠陥がないことを示すものではなく、その後に変更した設定は対象外で、ほかの関門の代わりにもなりません。ほかの関門とは、アクセシビリティ監査、承認されたデータ保護影響評価、お使いのプラットフォームでの復元訓練です。
